# DESIGN_DOCTRINE

## The Design

This is one product.

It is not three separate products glued together.

It is one coherent system composed of modular internal organs.

```text
One product.
Three internal organs.
Shared truth layer.
```

## Internal Organs

```text
Loop / project-512d
  Intelligence organ.
  Thinks, proves, evaluates, and produces artifacts.

Sun_Tan
  Bridge organ.
  Translates, hashes, signs, verifies, and coordinates packet exchange.

.Neon
  Continuity organ.
  Remembers origin, lineage, policy, claim state, and traversal history.
```

## Future Layering Principle

The first three organs are the foundation, not the ceiling.

The product is designed to support additional layers, kernels, adapters, and specialized organs over time.

Future layers may include:

- routing kernels
- memory kernels
- verification kernels
- interface kernels
- learning adapters
- local tool adapters
- product orchestration shells
- user-facing command surfaces

Every new layer must preserve the same rule:

```text
Unified product experience.
Modular internal responsibility.
Verified boundary exchange.
```

## Scaling Doctrine

The architecture is intended for unbounded compositional scale, not uncontrolled complexity.

Scale comes from stacking small verified kernels, not from making one giant runtime.

```text
Infinite product surface.
Finite contracts.
Verified exchanges.
Replaceable kernels.
```

A new layer may be added only when it has:

1. A clear owner role.
2. A bounded interface.
3. A deterministic packet or contract.
4. A verification rule.
5. A user-facing reason to exist.

If a layer cannot satisfy those requirements, it is not a layer yet. It is an idea waiting for a contract.

## Product Principle

The user should experience one product.

The developer should see clean subsystem boundaries.

The system should avoid both extremes:

- fragmented tools that feel disconnected
- one monolithic blob that cannot be audited or evolved

## Core Sentence

```text
Loop thinks.
Sun_Tan translates.
.NeoN remembers.
The product orchestrates all three.
More kernels may join, but each must earn a clean role.
```

## Build Rule

Every new feature must answer:

1. Which organ or kernel owns this responsibility?
2. What packet or contract crosses the boundary?
3. What verification happens before state is accepted?
4. How does the user experience this as one product?

## Anti-Drift Rule

If a feature makes the system feel like separate apps, redesign it.

If a feature collapses all responsibilities into one runtime, redesign it.

The correct shape is unified experience with modular organs and stackable kernels.
